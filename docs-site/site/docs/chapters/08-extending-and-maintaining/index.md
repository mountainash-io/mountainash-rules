# Chapter 8: Extending and Maintaining the Engines

Chapters 6 and 7 traced how `ExpressionRulesEngine` and `AccumulatorEngine` actually work: compiled ternary expressions, context binding, compatibility predicates, coalescing, and prime-encoded search. This chapter turns that understanding into change. It answers a narrower, more practical question than "how does this work" — "what exactly do I have to touch, and what will break if I get it wrong, when I add a match strategy, an accumulator strategy, an aggregate operation, or a hit policy?"

Use the recipes to identify the affected contracts before changing a dispatch branch. A new comparison, merge, aggregate or selection policy must preserve the public behavior already introduced, including validation, observability, batch evaluation and persisted metadata.

All source references below are pinned to the candidate HEAD commit `94659bb0c096485c87d329f09e944577427f129f` of [`mountainash-io/mountainash-rules`](https://github.com/mountainash-io/mountainash-rules).

### Backend Purity Enforcement

Chapter 1 introduced [backend-agnostic design](../01-rule-tables-and-decisions/index.md): the normal implementation boundary is `mountainash.relations` for relation operations and `mountainash.expressions` for expression construction, with the explicit native exceptions listed below. Chapter 6 showed [`DimensionCompiler`](../06-expression-execution-internals/index.md) building expression templates and the [`CTX_PREFIX` binding phase](../06-expression-execution-internals/index.md) injecting context columns. This section explains what the enforcement test checks and what still requires review.

The enforcement is [`tests/test_backend_purity.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/test_backend_purity.py). Its logic is deliberately narrow, and it is worth stating precisely rather than describing it as "a purity checker":

- It walks every `*.py` file under `src/mountainash_rules/` (via `SRC_ROOT.rglob("*.py")`), skipping only files whose name starts with `__` (so `__init__.py` and `__version__.py` are exempt, but every other module — including deeply nested ones — is parametrized as its own test case).
- For each file, it scans line by line. A line only becomes a candidate violation if its stripped text starts with `import ` or `from `, **and** that import statement's target starts with `polars`, `ibis`, or `narwhals` (bare or dotted, e.g. `from ibis.expr import types`).
- A matching line is excused only if it also contains a comment matching `#\s*allow:\s*\w+` on the *same line*.
- Any surviving matches fail that file's test with the offending `filename:lineno: statement` list.

This is a syntactic, per-import-line, per-source-file check — not a general static-analysis pass. It will not catch a native call reached through a value passed in from elsewhere without a matching `import`/`from` line in that file, a dynamic import (`importlib.import_module("polars")`), or backend-specific behavior expressed without an import at all (for example depending on a specific `dtype` string that only one backend produces). It also only scans `src/mountainash_rules/`; test and benchmark modules under `tests/` may import `polars`/`pandas` freely to build fixtures, and several do. Treat the test as a strong, fast guard against the common mistake — reaching for `import polars as pl` for convenience inside engine code — not as a proof that every code path is backend-agnostic. That proof still comes from running the change against every backend in `ALL_BACKENDS` (see [Prove behavior and maintain compatibility](#prove-behavior-and-maintain-compatibility)).

At this commit there are exactly three documented exceptions, each tagged with a reason the parametrized test accepts:

Each exception names a capability not yet available through the normal abstraction. Their import scopes differ: the empty-build import is at module level, while the regex and snapshot-read imports are inside functions. Before adding another native dependency, look for or contribute the corresponding Mountainash capability. If an exception is necessary, its same-line `# allow: <reason>` must document the specific missing capability. The test accepts a syntactic tag; review must decide whether the dependency and its behavioral restriction are justified.

The boundary also has a direction, not just a location. The accumulator engine depends on the filter engine (`AccumulatorEngine.apply` builds and reuses an `ExpressionRulesEngine` internally — see [`engines/accumulator/engine.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/engines/accumulator/engine.py)), and both engines depend on `core/`, never the reverse: `engines/accumulator -> engines/filter -> core`. A change that makes `core/` import from either engine package, or makes `engines/filter` import from `engines/accumulator`, is a structural regression even though `test_backend_purity.py` would not flag it — that test only checks *which packages* are imported, not *which internal modules* import which.

## Add a match or accumulator strategy

Filter matching and accumulator combination are separate questions over the same `MatchStrategy` value. Filter matching asks "does this one rule match this one context, as true/false/unknown?" (Chapter 3's [survival and ranking](../03-evaluating-decisions/index.md), built on Chapter 6's [compiled strategy families](../06-expression-execution-internals/index.md)). Accumulator combination asks "can these two rules coexist in one combination, and if so what is their merged constraint?" (Chapter 5's [lattice build](../05-combining-and-persisting-rules/index.md), built on Chapter 7's [compatibility and coalescing](../07-combination-search-internals/index.md)). A strategy can support one without the other — several already do — so these are two independent recipes, not one.

### Recipe: a new filter match strategy

1. **Enum.** Add the member to `MatchStrategy` in [`core/constants.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/core/constants.py). `MatchStrategy` is a lowercase `StrEnum`; the string value is what round-trips through YAML (`DimensionsMetadata.to_yaml`/`from_yaml`, Chapter 2's [YAML round-trip](../02-authoring-rule-libraries/index.md)), so pick a value you are willing to keep once rule libraries start persisting it.
2. **Validation.** `Dimension._validate_strategy_fields` in [`core/dimension.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/core/dimension.py) is a `model_validator(mode="after")` with one explicit `if self.match_strategy == ...` branch per strategy family — it is not a generic table. If your strategy needs specific fields (the way `RANGE` requires `range_min_field`/`range_max_field`) or a restricted `data_type` (the way `PREFIX`/`SUFFIX`/`CONTAINS`/`REGEX`/`CONTEXT_REGEX` require `str`, or `SET_MEMBERSHIP`/`SET_EXCLUSION` forbid `bool`), you must add a matching branch yourself. Omitting this step is not a no-op: an invalid `Dimension` (wrong `data_type`, missing required field) will construct successfully and only fail later, inside `compile_dimension`, with a less specific error.
3. **Compile.** Add a `case MatchStrategy.NEW_STRATEGY:` branch to `DimensionCompiler.compile_dimension`'s `match` statement in [`core/compiler.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/core/compiler.py), dispatching to a new `_compile_new_strategy(self, dim: Dimension) -> BaseExpressionAPI` method. That method must build its expression exclusively from `mountainash.expressions` (`ma.when`/`.then`/`.otherwise`, `.t_eq`/`.t_gt`/`.t_is_in`, and friends) and must return the ternary contract every other strategy returns: `1` for a hard match, `0` for unknown (a sentinel on either side), `-1` for a hard non-match. Nothing downstream special-cases individual strategies — `_scored_relation` (Chapter 3) computes `__survived` as "every active dimension's ternary is `>= 0`" and `__specificity` as "count of dimensions where the ternary is exactly `1`", over whichever `__t_<dim>` columns exist. Get the ternary values right and ranking is automatically correct; get them wrong (for example returning a native boolean instead of `{-1, 0, 1}`) and specificity silently miscounts.
4. **Selection metadata.** `selection_info_from_metadata` in [`core/hit_policy.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/core/hit_policy.py) lists both `RANGE` bound fields as rule inputs. `default_output_fields` excludes those inputs when inferring the business outputs used by `ANY`. Extend that classification for a new multi-column strategy; otherwise an extra constraint column can be mistaken for an output and cause an incorrect disagreement. This is separate from `RuleResult.explain()`, which reads per-dimension ternary columns.
5. **Tests.** Mirror the existing per-strategy classes in [`tests/core/test_compiler.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/core/test_compiler.py) (e.g. `TestExactCompilation`): hard match, sentinel rule value, sentinel context value, and — if the strategy is orderable/typed — the invalid-combination cases from `tests/core/test_dimension.py`. Then add the new strategy to `TestBackendAgnosticism`'s parametrize table in the same file, so it runs against every entry in `ALL_BACKENDS` from [`tests/conftest.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/conftest.py) (`polars`, `pandas`, `narwhals-polars`, `narwhals-pandas`, `ibis-duckdb`, `ibis-polars`, `ibis-sqlite`). Skipping this step is the single most common way a new strategy quietly works on Polars in development and fails on Ibis in production — the entire point of Chapter 1's backend-agnostic design is that this class of divergence should be caught by tests, not by users.

Shipping a filter-only strategy is a legitimate, complete piece of work. `NOT_EQUAL`, `EXACT_KEY`, `PREFIX`, `SUFFIX`, `CONTAINS`, `REGEX`, and `CONTEXT_REGEX` are filter-only today — none of them has accumulator support, and none needs it to be useful.

### Recipe: a new accumulator strategy

Making a strategy usable inside `AccumulatorEngine.build()` — whether it is the strategy you just added or an existing filter-only one — means implementing two things `AccumulatorCompiler` needs that `DimensionCompiler` does not: pairwise compatibility and coalescing.

1. **Compatible.** Add a `case MatchStrategy.NEW_STRATEGY:` branch to `compile_compatible`'s `match` statement in [`engines/accumulator/compiler.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/engines/accumulator/compiler.py), calling a new `_compatible_new_strategy(self, dim: Dimension) -> BaseExpressionAPI`. The expression operates on two rule rows from a cross-join: the combination-so-far (`co_<field>` columns) and the candidate rule (`<field>_rhs` columns) — this LHS/RHS naming is explained in Chapter 7's [compatibility predicates](../07-combination-search-internals/index.md) and is not repeated here. The existing `_compatible_exact` is the template to follow: it is `True` when the LHS is a sentinel, **or** the RHS is a sentinel, **or** both sides are concrete and equal. Your strategy's own definition of "can these two rule values coexist" replaces the third clause.
2. **Coalesce.** Add a matching `case` to `compile_coalesce`, returning a `list[BaseExpressionAPI]` — a list because some strategies need more than one output column (`RANGE` returns coalesced min and max). Follow the four-case sentinel table every existing coalesce method implements: both sides sentinel → stays sentinel; one side sentinel → take the other side's concrete value; both concrete → apply the strategy's own merge (intersection for `SET_MEMBERSHIP`, union for `SET_EXCLUSION`, the tighter bound for `GREATER_THAN`/`LESS_THAN`). This pattern is Chapter 7's [coalescing](../07-combination-search-internals/index.md) material in depth; this recipe only names where to add the new case.
3. **NA flag.** `compile_coalesce_na_flag` has a generic fallback (both-sides-sentinel, from `_sentinel_checks`) that already covers strategies with one sentinel pair. `RANGE` and the set strategies need — and your strategy may need — an explicit branch instead, because they track more than one underlying sentinel signal.
4. **Tests.** Mirror [`tests/accumulator/test_compiler.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/accumulator/test_compiler.py)'s per-strategy classes (both-hard-same-value, one-side-sentinel, both-sentinel-stays-sentinel, NA-flag correctness), then add a `build()`-level test in `tests/accumulator/test_engine.py` or `test_correctness.py` proving two rules that should combine do, and two that should not, don't.
5. **Invariant: order-independent combined meaning.** Compatibility must be symmetric, and coalescing must preserve the same constraint when operands are swapped or a valid multi-rule combination is regrouped. The canonical ordering guard fixes expansion order for one input table; it does not make an order-dependent strategy correct when the input rows are reordered. A small fixture can expose this: permute its rule rows and compare the effective combined constraints, including wildcard and concrete-value cases.
6. **Opting out is valid.** If the strategy has no sensible pairwise-combination semantics, leave `engines/accumulator/compiler.py` untouched. Its default `case _: raise ValueError(f"Strategy {dim.match_strategy.name} not supported by accumulator")` already reports a specific, actionable error the moment a `CONSTRAINT`-role dimension using that strategy reaches `AccumulatorEngine`. That error is the intended behavior for an unsupported strategy, not a gap to silently patch over.

## Add an aggregate or hit policy

### Recipe: a new aggregate operation

`AggregateOp` (Chapter 5's [aggregate model](../05-combining-and-persisting-rules/index.md)) is deliberately narrow: every member is a commutative, associative binary fold over one numeric or orderable column, with no dependency on how many rules have already been folded. That shape constrains what you can add without a larger design change — an operation like a running average cannot be expressed as a single-column fold the way `sum`/`min`/`max`/`product` are, because it needs a second running value (a count) alongside the accumulated numerator. Confirm your operation fits `fold(accumulator, next_value) -> new_accumulator` on one column before writing code.

1. **Enum.** Add the member to `AggregateOp` in [`engines/accumulator/aggregate.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/engines/accumulator/aggregate.py). `Aggregate.operation` is typed as `AggregateOp`, so Pydantic rejects any other string at construction — this is where validation for this recipe actually happens, confirmed by [`tests/accumulator/test_aggregate.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/accumulator/test_aggregate.py)'s `test_unknown_operation_rejected_at_construction`, which expects a Pydantic `ValidationError`, not a plain `ValueError`.
2. **Fold.** Add a `case AggregateOp.NEW_OP:` to the `match agg.operation:` block in `_expand_level`, [`engines/accumulator/engine.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/engines/accumulator/engine.py) (around the existing `SUM`/`MIN`/`MAX`/`PRODUCT` cases), expressing the fold over `acc = ma.col(agg_col)` and `rhs = ma.col(f"{agg.column_name}_rhs")` using `mountainash.expressions` methods, the same as `acc.add(rhs)` or `ma.least(acc, rhs)`. The trailing `case _: raise ValueError(...)  # pragma: no cover — validation blocks this at construction` branch stays; it is dead code only because step 1's Pydantic coercion already rejects anything outside `AggregateOp` before this method ever runs — it is not itself the validation, and leaving your new member out of this `match` while it exists in the enum would make that branch reachable again.
3. **Seed value.** Anchor creation seeds `__agg_<name>` directly from the raw rule column (`agg_exprs` in the same file, around where `ma.col(agg.column_name).alias(f"__agg_{agg.column_name}")` is built). If your fold needs a different starting value than "the first rule's own value" — for instance a count-based op seeded at `1` rather than at the row's value — that seeding expression needs to change too, not just the fold case.
4. **Tests.** Extend `tests/accumulator/test_aggregate.py` for the enum/validation surface, then add a `build()`/`apply()` test (alongside `tests/accumulator/test_lattice_properties.py` or `test_result.py`) asserting the accumulated value for a small, hand-computable rule set.
5. **Invariant: commutativity and associativity.** Check both `f(a, b) == f(b, a)` and `f(f(a, b), c) == f(a, f(b, c))` over the operation's valid domain. The fold should not acquire a different business meaning when rule order changes. Finite-precision floating-point arithmetic still needs an appropriate numerical comparison; mathematical associativity is not a promise of bit-identical floating-point results.
6. **Overflow is unguarded by design.** Aggregate-value overflow is backend-defined: only the combination identity (`__prime_product`) is `int64`-guarded, via the mechanisms Chapter 7 covers in [encoding identity and guarding integer bounds](../07-combination-search-internals/index.md). If your operation grows values faster than `sum` (as `product` already does), that is a known, accepted limitation to document on the new member, not a gap this recipe needs to close.

### Recipe: a new hit policy

The single-context evaluation path and `RuleResult.select()` share three functions in [`core/hit_policy.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/core/hit_policy.py): `ordering_keys`, `check_assertions` and `apply_cardinality`. That sharing keeps the policy definition consistent. Equivalent decisions still require the same complete survivor population and selection metadata: re-selection cannot recover rows already discarded by an earlier policy or filter, as [Chapter 3](../03-evaluating-decisions/index.md) explains.

1. **Enum.** Add the member to `HitPolicy` in `core/constants.py`.
2. **The three shared functions.** Extend whichever of `ordering_keys` (what "best" survivor order means for this policy), `check_assertions` (any invariant the full survivor set must satisfy — `UNIQUE`'s "at most one survivor", `ANY`'s "survivors must agree on output fields"), and `apply_cardinality` (whether the policy truncates to exactly one row, like `FIRST`/`PRIORITY`/`ANY`) your policy's semantics actually need. A policy that reuses `COLLECT`'s ordering and cardinality but adds a new assertion only needs a `check_assertions` branch.
3. **The batch path does not share those functions — mirror it by hand.** `ExpressionRulesEngine._evaluate_batch_frame` in [`engines/filter/engine.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/src/mountainash_rules/engines/filter/engine.py) reuses `ordering_keys` for sorting, but its `UNIQUE`/`ANY` assertion checks and `FIRST`/`PRIORITY`/`ANY` cardinality truncation are separate, inline logic built around `group_by("__context_id")` — because those operations need to happen per-context across every row of a batch relation at once, not one context's rows at a time the way `check_assertions`/`apply_cardinality` assume. Concretely: the `UNIQUE` check groups by `__context_id` and counts survivors per group; the cardinality truncation filters `ma.col("__rank").eq(ma.lit(1))` for `FIRST`/`PRIORITY`/`ANY` instead of calling `apply_cardinality`. Any new policy with an assertion or a cardinality rule must be re-implemented here in the per-context form, or Chapter 4's promised [batch/single-context consistency](../04-scoring-batches/index.md) will silently break for that one policy — single-context evaluation will enforce the new rule and batch evaluation will not (or vice versa).
4. **Companion fields.** `DimensionsMetadata._validate_hit_policy` in `core/dimension.py` only has a branch for `PRIORITY` requiring `priority_field`. Add an equivalent branch only if your policy needs its own required companion field.
5. **Tests.** Extend [`tests/core/test_hit_policy.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/core/test_hit_policy.py) (`TestOrderingKeys`, `TestPolicySemantics`, `TestResultSelect`) **and** `TestBatchHitPolicies` in [`tests/filter/test_batch_evaluation.py`](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/tests/filter/test_batch_evaluation.py) for the same policy — the two must be tested together precisely because they are two independent implementations of the same rule, per point 3.
6. **Invariant: total order.** `ordering_keys`' docstring states every returned key list ends with `("__rule_index", False)`. Every survivor set must resolve to a total order, or the "best" match could differ between two runs over the same rules and context. Any custom ordering you add must still end in `__rule_index` ascending as the final tiebreaker.

## Prove behavior and maintain compatibility

Every recipe above names its own tests; this section is what to check across all of them before calling a change done.

**Cross-backend behavior.** Use `ALL_BACKENDS` in `tests/conftest.py` and the `TestBackendAgnosticism` pattern in `tests/core/test_compiler.py` to exercise the same contract on supported configurations. Check their limits rather than equating a clean import scan with portability. `LIST_CAPABLE_BACKENDS` in `conftest.py` documents the Narwhals–Polars list-column restriction; the SQLite array/list skip is in `tests/core/test_compiler.py`. Review both the fixture selection and the strategy-specific skips when adding list operations.

**Single-context/batch consistency.** Any change that touches hit-policy dispatch or match-strategy compilation should be exercised through both `evaluate()`/`RuleResult.select()` and `evaluate_batch()` (Chapter 4), for the reason given in the hit-policy recipe above: the batch path has its own inline reimplementation of assertion and cardinality logic, not a shared call into `core/hit_policy.py`.

**Validation coverage.** `tests/core/test_dimension.py` groups tests by validator branch (`TestRegexPatternValidation`, `TestSetStrategyValidation`, `TestExistingValidationUnchanged`) — a new strategy or policy should add a class in the same shape: at least one test proving the valid configuration is accepted, and one proving each invalid configuration your new validator branch rejects is actually rejected, with a message that names the field or strategy at fault the way the existing branches do.

**Compatibility.** `MatchStrategy` and `HitPolicy` strings are serialized with dimension metadata; `AggregateOp` strings are serialized with aggregate models, including the separate `aggregates` entries in a lattice manifest. Adding a value can preserve the new code's ability to read older artifacts if existing meanings remain unchanged, but older code cannot necessarily read artifacts using the new value. Renaming or removing an existing value breaks artifacts that still reference it. Review both directions of the persisted contract, using Chapter 2's metadata round-trip and Chapter 5's [lattice save/load](../05-combining-and-persisting-rules/index.md) workflows.

For the repository's branching, pull-request, and review process — which applies to every change in this chapter identically and is not specific to this package's engines — see [CONTRIBUTING.md](https://github.com/mountainash-io/mountainash-rules/blob/94659bb0c096485c87d329f09e944577427f129f/CONTRIBUTING.md).
