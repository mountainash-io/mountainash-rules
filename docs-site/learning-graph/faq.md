# Mountainash Rules Frequently Asked Questions

## General Architecture and Design

### What is mountainash-rules and what problems does it solve?

Mountainash-rules is a vectorized, backend-agnostic business rules engine for evaluating business logic stored as tabular data. It solves two fundamental classes of problems. First, "find the best matching rule" problems such as pricing lookup, eligibility checking, and configuration selection, where a context (a set of input values) must be matched against a table of rules to find the single most specific match. Second, combinatorial accumulation problems such as "which benefits apply and what is their total value," where all maximal consistent subsets of rules must be identified and their associated values accumulated. Rather than implementing rules as imperative if/else chains, mountainash-rules treats rules as rows in a DataFrame and evaluates them using vectorized expressions. This means thousands of rules are evaluated simultaneously in a single pass, with no per-rule branching or loops. The engine is backend-agnostic, meaning the same rule definitions work across different DataFrame backends (Polars, Narwhals, Ibis) through mountainash's expression and relation abstractions.

### What are the two engines and when should I use each one?

Mountainash-rules provides two complementary engines. The ExpressionRulesEngine performs single-pass vectorized filter evaluation, producing a ranked list of surviving rules ordered by specificity. Use it when you need to find one or a few best-matching rules from a table, such as looking up the correct price tier, selecting a configuration profile, or checking eligibility. It is fast and straightforward because it evaluates all rules in a single pass without combinatorial expansion. The AccumulatorEngine solves the harder problem of finding all maximal consistent subsets of rules and accumulating their associated values. Use it when rules can combine, such as stacking discount rules, aggregating benefit entitlements, or computing totals across compatible rule combinations. The AccumulatorEngine builds a lattice of all valid combinations, filters dominated subsets, and produces accumulated aggregates with full provenance. If your problem is "which single rule wins," use ExpressionRulesEngine. If your problem is "which rules stack and what is their combined effect," use AccumulatorEngine.

### What does "backend-agnostic" mean in the context of mountainash-rules?

Backend-agnostic means that rule definitions, dimension metadata, and engine configurations are expressed in terms of mountainash's abstract expression and relation APIs rather than being tied to a specific DataFrame library. The DimensionCompiler and AccumulatorCompiler produce mountainash expression objects (using col, lit, when, t_col and similar constructors), and the engines operate through the mountainash relation interface (relation(), with_columns, filter, collect). At evaluation time, these abstract expressions are compiled to the concrete backend in use, whether that is Polars, Narwhals, or Ibis. This means the same DimensionsMetadata schema and engine configuration can evaluate rules stored in a Polars DataFrame today and an Ibis-backed database table tomorrow, without changing the rule definitions. The one exception is the AccumulatorEngine's lattice-building phase, which currently materializes to Polars for its internal combinatorial expansion. However, the external API remains backend-agnostic, and this materialization is an implementation detail that may change in future versions.

### What is the role of Pydantic in mountainash-rules?

Pydantic provides the model validation layer for all configuration objects in mountainash-rules. The Dimension class, DimensionsMetadata collection, and Aggregate model are all Pydantic models, which means they enforce type constraints, validate field values, and provide clear error messages when configurations are incorrect. For example, when you define a Dimension with a RANGE strategy, the Pydantic validator ensures that low and high field names are provided and that the data type is numeric. The DimensionsMetadata class validates that dimension names are unique, that field references are consistent, and that CONTEXT_KEY dimensions are properly configured. This validation-at-definition-time approach catches configuration errors early, before any data is processed, rather than producing cryptic runtime errors during evaluation. Pydantic also provides serialization support, making it straightforward to store dimension metadata as JSON or load it from configuration files.

### How does mountainash-rules differ from traditional rule engines like Drools or business rule management systems?

Traditional rule engines typically represent rules as imperative condition-action pairs and evaluate them through forward or backward chaining, pattern matching (Rete algorithm), or sequential if/else evaluation. Mountainash-rules takes a fundamentally different approach by representing rules as rows in a table and evaluating them using vectorized DataFrame operations. This tabular approach has several advantages. First, rules are data, not code, meaning they can be stored in spreadsheets, databases, or CSV files and edited by non-programmers. Second, evaluation is vectorized, meaning all rules are evaluated simultaneously in a single pass rather than one at a time, which scales efficiently to thousands of rules. Third, the engine produces explainability output showing exactly why each rule matched or failed, with per-dimension ternary outcomes. Fourth, the accumulator engine solves combinatorial problems that traditional rule engines handle poorly or not at all. The trade-off is that mountainash-rules is specialized for tabular matching and accumulation problems; it does not support arbitrary rule chaining or complex inference.

### What is a Context Object and how is it used?

A Context Object is a dictionary-like structure that represents the input values to be matched against rules. When you evaluate rules, you provide a context containing the values for each dimension, such as a customer's region, product category, or transaction amount. The ExpressionRulesEngine extracts values from the context for each dimension and binds them into the evaluation pipeline using context value extraction. Sentinel values in the context (None or the special NOT_PROVIDED sentinel) indicate that a dimension's value is unknown, which triggers ternary UNKNOWN outcomes for that dimension rather than TRUE or FALSE. The context is validated against the DimensionsMetadata to ensure all required dimension values are present. For the AccumulatorEngine, CONTEXT_KEY dimensions in the context are used for partition key filtering, selecting only the relevant partition of the lattice before applying the context to accumulate results.

### How are rules stored and what format do they use?

Rules are stored as rows in a DataFrame, where each row represents one rule and columns correspond to dimension values and output fields. Any DataFrame format supported by mountainash's relation system can be used, including Polars DataFrames, pandas DataFrames (via Narwhals), or database tables (via Ibis). For a RANGE dimension like "age," the rule table has two columns (e.g., age_low and age_high). For an EXACT dimension like "region," the table has a single column with the exact match value. Sentinel values (null, empty string, or special numeric sentinels) in rule columns indicate "don't care" wildcards, meaning the rule matches any value for that dimension. Output columns (prices, labels, configuration values) are carried through evaluation alongside the matching dimensions. This tabular format makes rules easy to author in spreadsheets, export from databases, or generate programmatically.

### What are the 12 modules in the mountainash-rules package?

The mountainash-rules package is organized into modules covering foundation concepts, dimension modeling, expression compilation, engine execution, and results. The core modules include: the Dimension module defining the Dimension class, DimensionsMetadata, and DimensionRole enum; the MatchStrategy module defining the 11 match strategy types; the DimensionCompiler module for translating dimensions into expressions; the ExpressionRulesEngine module implementing single-pass filter evaluation; the RuleResult module for accessing and explaining evaluation outcomes; the AccumulatorCompiler module for compatible and coalesce expression generation; the AccumulatorEngine module implementing lattice-based combinatorial evaluation; the Lattice module for the lattice data structure; the AccumulatorResult module for accumulated aggregates and provenance; the Aggregate module for defining accumulation functions; the Context module for context value extraction and sentinel handling; and the partition module for partition key filtering and build_all/apply_auto convenience functions.

## Ternary Logic and Sentinel Values

### What is ternary logic and why does mountainash-rules use it?

Ternary logic extends classical two-valued (TRUE/FALSE) logic with a third value: UNKNOWN. In mountainash-rules, ternary logic is represented numerically as 1 (TRUE), 0 (UNKNOWN), and -1 (FALSE). This three-valued system is essential because real-world rule evaluation frequently encounters situations where a dimension value is missing or not applicable. For example, if a rule specifies a region constraint but the context does not provide a region value, classical logic would force a binary match/no-match decision. Ternary logic instead produces UNKNOWN, meaning "this rule might match but we cannot confirm." This enables "don't care" wildcard matching where rules with sentinel (null) dimension values produce UNKNOWN, which does not eliminate them from consideration. The survival computation treats both TRUE (1) and UNKNOWN (0) as surviving, while only FALSE (-1) eliminates a rule. This means wildcard rules survive alongside specifically matched rules, and the specificity scoring system then ranks specific matches higher than wildcard matches.

### What are sentinel values and how do they work?

Sentinel values are special marker values that indicate "no constraint" or "don't care" for a dimension in a rule row. Mountainash-rules uses four sentinel values with both string and numeric variants: null (None/NaN) for missing values, empty string for string dimensions, and special numeric constants for integer and float dimensions. When the DimensionCompiler encounters a sentinel value in a rule column, it generates a ternary expression that evaluates to UNKNOWN (0) rather than TRUE (1) or FALSE (-1). This is the mechanism behind wildcard matching. A rule with a null region field matches any region with an UNKNOWN outcome, while a rule with "US" matches the US context with TRUE and a non-US context with FALSE. Sentinel values propagate through the ternary expression system predictably: if any dimension in a rule has a sentinel value, that dimension contributes UNKNOWN to the survival computation, reducing the rule's specificity score but not eliminating it. The sentinel-aware ternary system ensures consistent behavior regardless of whether sentinels appear in the rule table or the context.

### How does ternary logic affect rule matching outcomes?

When evaluating a context against rules, each dimension produces a ternary outcome per rule: TRUE (the rule's constraint matches the context value), FALSE (the constraint contradicts the context value), or UNKNOWN (either the rule has a sentinel/wildcard for this dimension, or the context value is missing). The survival computation combines all dimension outcomes for each rule. A rule survives if none of its dimensions evaluated to FALSE, meaning all dimensions are either TRUE or UNKNOWN. A rule is eliminated if any dimension evaluated to FALSE. Among surviving rules, specificity scoring counts the number of TRUE outcomes. A rule with three TRUE dimensions and one UNKNOWN is more specific than a rule with two TRUE dimensions and two UNKNOWN values. This layered approach means the engine naturally handles partial information, wildcard rules, and default fallback rules in a single evaluation pass without requiring explicit priority or ordering annotations on the rules themselves.

### Can I have a rule that matches everything (a default rule)?

Yes. A default rule is simply a rule row where all dimension columns contain sentinel values (null or empty). Since every dimension evaluates to UNKNOWN for this rule, it always survives the survival computation because no dimension is FALSE. However, its specificity score is zero (no TRUE dimensions), so it ranks below any rule that has at least one specific match. This is exactly the desired behavior for a default or fallback rule: it is always available as a match but is outranked by any more specific rule. You do not need to assign a special priority or "default" flag. The specificity ranking system handles this automatically. If you want multiple fallback levels, you can create rules with progressively more sentinel values, and the specificity scoring naturally orders them from most specific to least specific.

### What happens when the context is missing a value for a dimension?

When a context does not provide a value for a dimension (the value is None or NOT_PROVIDED), the context value extraction phase assigns a sentinel value for that dimension. During evaluation, the DimensionCompiler's expressions compare the sentinel context value against each rule's dimension column. Since the context value is a sentinel, the ternary expression evaluates to UNKNOWN (0) for every rule, regardless of what value the rule specifies for that dimension. This means no rule is eliminated based on that dimension, and the dimension does not contribute to specificity scoring. Effectively, the missing context value causes that dimension to be ignored in the evaluation. All rules survive on that dimension, and ranking is determined by the remaining dimensions. This behavior is intentional: incomplete information should not eliminate potentially valid rules. The explain method on RuleResult will show UNKNOWN for that dimension, making it clear which dimensions were indeterminate.

## Match Strategies and Dimensions

### What are the 11 MatchStrategy types?

The MatchStrategy enum defines 11 comparison strategies: EXACT (equality match), NOT_EQUAL (inequality match), RANGE (value falls within a low-high interval), GREATER_THAN (value exceeds a threshold), LESS_THAN (value falls below a threshold), PREFIX (string starts with a pattern), SUFFIX (string ends with a pattern), CONTAINS (string includes a substring), REGEX (string matches a regular expression), SET_MEMBERSHIP (value belongs to a set), and SET_EXCLUSION (value does not belong to a set). Each strategy has data type constraints; numeric strategies (RANGE, GREATER_THAN, LESS_THAN) require numeric columns, string strategies (PREFIX, SUFFIX, CONTAINS, REGEX) require string columns, and set strategies (SET_MEMBERSHIP, SET_EXCLUSION) work with list or delimited string columns. The strategy determines how the DimensionCompiler generates the comparison expression and how sentinel values are detected for that dimension type.

### How does the EXACT match strategy work?

EXACT is the most common match strategy, performing equality comparison between the context value and the rule column value. When compiled, it produces a ternary expression that evaluates to TRUE (1) if the context value equals the rule value, FALSE (-1) if they differ, and UNKNOWN (0) if either value is a sentinel. The sentinel check examines the rule column for null, empty string, or numeric sentinel values before performing the equality test. EXACT works with any comparable data type: strings, integers, floats, dates, and booleans. It is the default strategy when no strategy is specified. A typical use case is matching a customer's country code against a rule's country column, or matching a product SKU against a rule's product column. The NOT_EQUAL strategy is the logical inverse, evaluating to TRUE when values differ and FALSE when they are equal.

### How does the RANGE match strategy work?

RANGE checks whether a context value falls within a closed interval defined by two rule columns: a low bound and a high bound. The Dimension definition for a RANGE strategy requires specifying both a low_field and a high_field. The compiled expression evaluates to TRUE if low <= context_value <= high, FALSE if the context value is outside the interval, and UNKNOWN if either bound is a sentinel value. Sentinel handling for RANGE is nuanced: if only the low bound is a sentinel, the check becomes context_value <= high (open lower bound). If only the high bound is a sentinel, the check becomes low <= context_value (open upper bound). If both are sentinels, the result is UNKNOWN. RANGE is commonly used for age bands, price tiers, date ranges, and any dimension with continuous numeric intervals. The GREATER_THAN and LESS_THAN strategies are simplified versions that check only one side of the comparison.

### How do the string match strategies (PREFIX, SUFFIX, CONTAINS, REGEX) work?

The four string match strategies handle pattern-based matching on string dimension values. PREFIX checks whether the rule's pattern value is a prefix of the context value using a starts-with operation. SUFFIX checks whether the pattern is a suffix using an ends-with operation. CONTAINS checks whether the pattern appears anywhere in the context value as a substring. REGEX compiles the rule's pattern as a regular expression and tests whether the context value matches. All four strategies include sentinel detection: if the rule's pattern column is null or empty string, the result is UNKNOWN rather than FALSE. The DimensionCompiler generates these as ternary expressions using mountainash's string operation functions. An important detail is that the Dimension Validator enforces that string strategies are only used with string-typed columns, and REGEX patterns are validated at definition time when possible. String strategies are particularly useful for hierarchical codes (PREFIX matching "US" against "US-CA-SF"), file paths (SUFFIX matching ".pdf"), and flexible text matching.

### How do SET_MEMBERSHIP and SET_EXCLUSION strategies work?

SET_MEMBERSHIP checks whether a context value is a member of a set defined in the rule column. The set can be stored as a list column or as a delimited string that is parsed into a set. The expression evaluates to TRUE if the context value is in the set, FALSE if it is not, and UNKNOWN if the set column is null or empty. SET_EXCLUSION is the inverse, evaluating to TRUE if the context value is not in the set and FALSE if it is. These strategies are useful for rules that apply to multiple discrete values without requiring separate rows for each value. For example, a pricing rule that applies to regions "US", "CA", and "UK" can use a single row with SET_MEMBERSHIP on a regions column containing those values, rather than three separate rows with EXACT matching. The sentinel handling treats an empty or null set as "don't care" (UNKNOWN) rather than "matches nothing" (FALSE), which is consistent with the wildcard semantics throughout the system.

### What is the DimensionRole enum and what are CONSTRAINT and CONTEXT_KEY?

DimensionRole has two values that determine how a dimension participates in evaluation. CONSTRAINT (the default) means the dimension is a matching criterion: the engine compares the context value against the rule column value to determine whether the rule matches. All standard matching behavior (ternary evaluation, specificity scoring, survival computation) applies to CONSTRAINT dimensions. CONTEXT_KEY means the dimension is a partition key rather than a matching criterion. CONTEXT_KEY dimensions are not evaluated for matching; instead, they are used to filter the rule table (or lattice) to the relevant partition before evaluation begins. For example, if you have a "customer_id" dimension with CONTEXT_KEY role, the engine first filters rules to only those belonging to the given customer, then evaluates the remaining CONSTRAINT dimensions. In the AccumulatorEngine, CONTEXT_KEY dimensions define the partition boundaries for lattice building, so each partition's lattice contains only the rules for that key value.

### What is the Dimension class and how do I configure it?

The Dimension class is a Pydantic model that describes a single matching criterion in a rule table. It has several key fields: name (the logical dimension name), strategy (the MatchStrategy enum value), role (CONSTRAINT or CONTEXT_KEY), field (the rule table column name for single-column strategies), low_field and high_field (for RANGE strategy), and data type information. The Dimension class uses Pydantic validation to enforce consistency. For example, RANGE dimensions must specify low_field and high_field, string strategies must reference string-typed columns, and CONTEXT_KEY dimensions have restrictions on which strategies they can use. Field resolution maps the logical dimension name to physical column names in the rule table, handling cases where the column name differs from the dimension name. You can create dimensions individually and assemble them into a DimensionsMetadata collection, which validates the complete set of dimensions for consistency and uniqueness.

### What is DimensionsMetadata and why is it a collection?

DimensionsMetadata is a Pydantic model that holds an ordered collection of Dimension objects and provides group-level validation and access methods. It exists as a collection rather than a simple list because the set of dimensions has cross-cutting constraints: dimension names must be unique, field references must not collide, and the combination of CONSTRAINT and CONTEXT_KEY dimensions must be internally consistent. DimensionsMetadata also provides convenience methods for accessing dimensions by name, iterating over CONSTRAINT-only or CONTEXT_KEY-only subsets, and extracting the complete set of rule table columns required. Both engines accept DimensionsMetadata as their primary configuration input. The DimensionCompiler and AccumulatorCompiler iterate over the metadata to generate expressions for each dimension. By centralizing dimension definitions in DimensionsMetadata, the system ensures that all components share the same understanding of the rule schema.

### What are Data Type Constraints for match strategies?

Data Type Constraints are validation rules that restrict which match strategies can be used with which column data types. Numeric strategies (RANGE, GREATER_THAN, LESS_THAN) require numeric columns (integers or floats) because they perform ordered comparisons. String strategies (PREFIX, SUFFIX, CONTAINS, REGEX) require string columns because they perform text pattern operations. EXACT and NOT_EQUAL work with any comparable type. SET_MEMBERSHIP and SET_EXCLUSION require list-typed or delimited-string columns. These constraints are enforced by the Dimension Validator at definition time, when you create a Dimension object. If you attempt to define a RANGE strategy on a string column, validation fails immediately with a clear error message rather than producing incorrect results at evaluation time. Data type constraints also influence how sentinel values are detected; numeric sentinels differ from string sentinels, and the DimensionCompiler uses the data type to select the correct sentinel detection logic.

## ExpressionRulesEngine and Results

### How does the ExpressionRulesEngine evaluation pipeline work?

The ExpressionRulesEngine performs evaluation in a single pass through four phases. First, the context binding phase extracts values from the context object and binds them as literal expressions. Second, the dimension expression phase applies the compiled expressions for each dimension, producing a ternary column (1/0/-1) per dimension per rule. Third, the survival computation phase combines all dimension outcomes per rule: if any dimension is FALSE (-1), the rule is eliminated; otherwise it survives with a combined outcome. Fourth, the specificity scoring and rank assignment phase counts the number of TRUE (1) outcomes per surviving rule and assigns ranks accordingly. The highest-specificity rule gets rank 1. The result is a RuleResult object containing the original rule data augmented with __survived, __specificity, and __rank columns. This entire pipeline executes as vectorized DataFrame operations, meaning all rules are processed simultaneously without per-rule iteration.

### What is the DimensionCompiler and what does it produce?

The DimensionCompiler translates DimensionsMetadata into a set of mountainash expression templates, one per dimension. Each template is a ternary expression that, when given a context value, produces a column of 1/0/-1 outcomes for every rule row. The compiler dispatches on the MatchStrategy to generate the appropriate comparison logic: compile_exact_expression for EXACT and NOT_EQUAL, compile_range_expression for RANGE, compile_string_match for PREFIX/SUFFIX/CONTAINS, compile_regex_expression for REGEX, compile_set_expression for SET_MEMBERSHIP/SET_EXCLUSION, and compile_threshold_expression for GREATER_THAN/LESS_THAN. Each compiled expression wraps the comparison in sentinel-aware ternary logic, checking for sentinel values in both the rule column and the context before performing the comparison. The expressions are backend-agnostic mountainash expression objects, so they work across any supported DataFrame backend.

### What is specificity scoring and how does ranking work?

Specificity scoring quantifies how precisely a surviving rule matches the context. For each surviving rule, the engine counts the number of dimensions that evaluated to TRUE (1) rather than UNKNOWN (0). A rule where all five dimensions are TRUE has specificity 5; a rule where three are TRUE and two are UNKNOWN has specificity 3. Higher specificity means a more precise match. Rank assignment orders survivors by descending specificity, with rank 1 being the most specific. Ties in specificity are preserved as equal ranks. This scoring system provides a natural and intuitive ordering: a rule that explicitly matches the context on every dimension outranks a rule that matches on some dimensions and wildcards the rest. You do not need to manually assign priorities to rules. The specificity system derives priority from the rule data itself, making rule tables easier to maintain and reason about.

### What is the RuleResult class and what accessors does it provide?

RuleResult is a wrapper around the evaluated DataFrame that provides convenient accessors for common query patterns. The survivors accessor returns all rules that survived evaluation (not eliminated by any FALSE dimension). The best_match accessor returns the single highest-ranked survivor (rank 1). The count accessor returns the number of survivors. The active_dimensions accessor lists which dimensions contributed TRUE outcomes for the best match. The explain method provides per-rule explainability, showing the ternary outcome for each dimension so you can understand exactly why a rule matched, partially matched, or was eliminated. The at_least filter returns survivors meeting a minimum specificity threshold. The top_n filtering returns the N highest-ranked survivors. The min_specificity filter returns only survivors with specificity at or above a given score. RuleResult also exposes observability columns (__survived, __specificity, __rank) that can be used for logging, auditing, or feeding into downstream systems.

### How does the explain method work and what does it show?

The RuleResult.explain() method provides per-rule explainability by exposing the ternary outcome column for each dimension. For a given rule (identified by index or the best match), explain returns a dictionary mapping dimension names to their ternary outcomes: TRUE (1) means the dimension matched the context, FALSE (-1) means it contradicted, and UNKNOWN (0) means either the rule had a wildcard or the context value was missing. This makes it straightforward to understand why a rule survived or was eliminated. For example, if a pricing rule was eliminated, explain might show {"region": 1, "product": -1, "tier": 0}, revealing that the region matched, the product contradicted, and the tier was a wildcard. The explain output is generated from the observability columns that the engine computes during the dimension expression phase, so it adds no additional computation cost. This explainability is a key advantage of the vectorized approach: because every dimension is evaluated explicitly, the outcomes are always available for inspection.

### What is the difference between the convenience and advanced paths?

Engine construction offers two paths. The convenience path accepts a DimensionsMetadata object and a DataFrame directly, performing compilation and evaluation in a single call. This is suitable for one-time evaluations or simple use cases where you evaluate a context against a rule table and retrieve the result. The advanced path separates engine construction from evaluation. You create an ExpressionRulesEngine instance with the DimensionsMetadata, which pre-compiles all dimension expressions. You then call the engine's evaluate method repeatedly with different contexts, reusing the compiled expressions each time. The advanced path is more efficient when evaluating many contexts against the same rule table, because compilation (which involves generating and optimizing expression templates) happens once rather than per evaluation. The advanced path also gives you access to intermediate objects like the compiled dimension expressions, which can be useful for debugging or custom evaluation workflows.

### How do the at_least, top_n, and min_specificity filters work?

These are post-evaluation filters on RuleResult that narrow the set of survivors. The at_least filter returns survivors where a minimum number of dimensions evaluated to TRUE, providing a way to require a baseline level of matching confidence. For example, at_least(3) returns only survivors where at least three dimensions specifically matched the context. The top_n filter returns the N highest-ranked survivors, useful when you want the top 5 matches rather than just the best. The min_specificity filter returns survivors whose specificity score meets or exceeds a threshold value. These filters can be combined: you might first apply min_specificity to ensure quality, then top_n to limit quantity. All filters return new RuleResult objects, so the original result is preserved. These filters operate on the already-computed __specificity and __rank columns, so they add negligible computation cost.

### What are the observability columns and how can I use them?

The ExpressionRulesEngine adds three observability columns to the evaluated DataFrame: __survived (boolean indicating whether the rule passed survival computation), __specificity (integer count of TRUE dimensions), and __rank (integer rank among survivors, 1 being highest). Additionally, the engine preserves the per-dimension ternary outcome columns that feed into the explain method. These columns serve multiple purposes. For debugging, you can inspect why specific rules were eliminated by looking at per-dimension outcomes. For logging and auditing, you can record the full evaluated DataFrame to trace how decisions were made. For downstream processing, you can use __rank and __specificity in custom logic beyond what RuleResult's built-in accessors provide. The observability columns are always computed and always present in the result; there is no performance penalty for having them available.

## AccumulatorEngine and Lattice

### What problem does the AccumulatorEngine solve that the ExpressionRulesEngine cannot?

The ExpressionRulesEngine finds which individual rules match a context and ranks them. It answers "which single rule is the best match." The AccumulatorEngine solves a fundamentally different problem: given a set of rules, find all maximal consistent subsets and accumulate their combined values. For example, consider benefit rules where a customer might qualify for multiple benefits simultaneously: a loyalty discount, a volume discount, and a seasonal promotion. The ExpressionRulesEngine would rank these individually, but the AccumulatorEngine finds which combinations are mutually consistent (their dimension constraints do not contradict) and computes the total accumulated value for each valid combination. It answers "which rules can stack together and what is their combined effect." This requires combinatorial analysis that the single-pass filter approach cannot provide.

### How does prime number encoding work in the AccumulatorEngine?

Prime number encoding assigns a unique prime number to each rule in the input table. When rules are combined, their prime numbers are multiplied together to produce a composite number that uniquely identifies the combination. Because prime factorization is unique (the fundamental theorem of arithmetic), every combination of rules has a unique prime product, and any prime product can be factored to recover the exact set of rules it represents. This provides two powerful capabilities: combination identity (you can compare two combinations for equality by comparing their prime products) and subset detection (combination A is a subset of combination B if B's prime product is divisible by A's prime product, checked via modular arithmetic). The prime table sieve generates primes on demand, and the get_prime function maps rule indices to their assigned primes. The checked_multiply function performs multiplication with overflow detection, since int64 prime products can overflow with large rule sets, which is why partition keys are important for keeping partition sizes manageable.

### What are the phases of lattice building?

The AccumulatorEngine builds its lattice through five phases. First, partition: if CONTEXT_KEY dimensions exist, the rule table is partitioned by key values so each partition is processed independently. Second, prime assignment: each rule in the partition receives a unique prime number. Third, anchor creation: each individual rule becomes a depth-1 node in the lattice with its prime number as its identity. Fourth, level expansion: the engine iteratively combines compatible anchors and existing nodes to create higher-depth combinations, checking that dimensions are compatible (their constraints do not contradict) and coalescing dimension values for the combined node. This continues until no new valid combinations can be formed. Fifth, frontier filter: dominated combinations (those that are strict subsets of larger valid combinations) are removed, leaving only the maximal consistent subsets. The result is a Lattice object containing all maximal combinations with their coalesced dimension values, accumulated aggregates, and prime product identities.

### What is the frontier filter and why is it needed?

The frontier filter removes dominated combinations from the lattice after level expansion. A combination is dominated if it is a strict subset of another valid combination. For example, if rules A, B, and C are all mutually compatible, the lattice expansion phase will generate combinations {A}, {B}, {C}, {A,B}, {A,C}, {B,C}, and {A,B,C}. The frontier filter removes {A}, {B}, {C}, {A,B}, {A,C}, and {B,C} because they are all subsets of {A,B,C}. Only maximal combinations survive. This is essential because dominated combinations represent suboptimal accumulations. If a customer qualifies for all three discounts, reporting the two-discount combinations would be misleading. The frontier filter uses prime product divisibility for efficient subset detection: combination X is dominated by combination Y if Y's prime product is divisible by X's prime product and they are not equal. The checked_multiply function ensures overflow is detected, since this divisibility check requires correct prime products.

### What are compatible and coalesce expressions?

These are two types of expressions generated by the AccumulatorCompiler for the lattice-building phase. Compatible expressions check whether two rules can be combined without contradiction. For each CONSTRAINT dimension, the compatible expression determines whether the dimension values from two rules can coexist. For example, compatible_exact checks if two EXACT values are either equal or one is a sentinel (wildcard). Compatible_range checks if two ranges overlap. If any dimension is incompatible, the rules cannot be combined. Coalesce expressions determine the combined dimension value when two compatible rules are merged. For example, coalesce_exact takes the non-sentinel value (or either value if both are equal). Coalesce_range takes the intersection of the two ranges (the tighter bounds). The coalesce_na_flag tracks whether the coalesced value came from a sentinel, which affects specificity-like reasoning in the lattice. Together, these expressions drive the level expansion phase, determining which combinations are valid and what dimension values the combined node carries.

### What is the Lattice class and what does it contain?

The Lattice class is the data structure produced by the AccumulatorEngine's build phase. It contains a DataFrame where each row represents a maximal consistent combination of rules. Key columns include: the prime product column (uniquely identifying which rules are in the combination), combination depth (how many rules are combined), coalesced columns (the merged dimension values for the combination), NA flag columns (tracking which coalesced values originated from sentinels), accumulated aggregate columns (the summed or otherwise aggregated output values), and the partition key column (if CONTEXT_KEY dimensions are present). The Lattice is pre-computed and can be reused across multiple context evaluations without rebuilding. When you apply a context to a Lattice, the engine filters to the relevant partition (if applicable), evaluates the coalesced dimension values against the context, and returns an AccumulatorResult with the matching combinations and their accumulated values.

### What are coalesced columns and NA flag columns?

When two rules are combined in the lattice, their dimension values are merged through coalesce expressions. The resulting merged values are stored in coalesced columns. For example, if rule A has region="US" and rule B has region=null (wildcard), the coalesced region column for the {A,B} combination contains "US" (the non-sentinel value). NA flag columns are companion boolean columns that track whether a coalesced value originated from a sentinel. In the example above, the NA flag for region would be FALSE for the {A,B} combination (the coalesced value is a real value from rule A), but TRUE for a combination where both contributing rules had null region values. NA flags are important because they distinguish between a coalesced value that represents a real constraint and one that is effectively a wildcard, which can affect downstream evaluation when a context is applied to the lattice.

### What is combination depth and why does it matter?

Combination depth is the number of individual rules that make up a combination in the lattice. An anchor (single rule) has depth 1, a pair has depth 2, and so on. Depth is tracked as a column in the Lattice DataFrame and is accessible through the AccumulatorResult's depths accessor. Depth matters for several reasons. First, it provides an ordering metric: deeper combinations represent more rules stacking together, which may be more or less desirable depending on the business context. Second, it relates to the accumulation magnitude: a depth-5 combination accumulates values from five rules, typically producing a larger aggregate than a depth-2 combination. Third, depth interacts with the frontier filter: the maximal combinations in the frontier are typically the deepest for their compatible set. Fourth, depth is useful for validation and testing, confirming that the lattice is producing combinations of expected sizes.

### How do partition keys work in the AccumulatorEngine?

Partition keys divide the rule table into independent subsets that are processed separately during lattice building. Dimensions with CONTEXT_KEY role serve as partition keys. For example, if "customer_id" is a CONTEXT_KEY dimension, the rule table is partitioned by customer_id, and a separate lattice is built for each customer. This serves two purposes. First, correctness: rules for different customers should never be combined together, and partitioning enforces this. Second, performance: the combinatorial expansion in lattice building is exponential in the number of rules, so keeping partitions small prevents prime product overflow and keeps computation tractable. The build_all convenience function builds lattices for all partitions, and apply_auto selects the correct partition lattice when a context is applied. Partition key filtering uses the CONTEXT_KEY dimension values from the context to select the relevant partition before evaluation.

### What is the int64 prime product overflow boundary?

Prime products are stored as int64 integers, which have a maximum value of approximately 9.2 x 10^18. As rules are combined, their prime products are multiplied together, and this product can exceed int64 range. The checked_multiply function detects overflow before it occurs, ensuring that invalid combinations are not silently produced. The practical impact is that there is an upper limit on how many rules can be combined in a single partition before overflow occurs. The exact limit depends on the prime numbers assigned (larger primes for higher-indexed rules mean faster overflow), but as a rough guide, combinations of 15-20 rules from a table of hundreds may approach the boundary. This is why partition keys are important: by dividing rules into smaller partitions, each partition's combinatorial space stays within the int64 boundary. When evaluating whether CONTEXT_KEY partitioning is necessary, the prime product overflow boundary is a key consideration alongside correctness.

### How does the AccumulatorResult differ from RuleResult?

AccumulatorResult and RuleResult serve different engines and provide different information. RuleResult wraps individually ranked rules from the ExpressionRulesEngine, providing survivors, best match, specificity ranking, and per-dimension explain output. AccumulatorResult wraps lattice combinations from the AccumulatorEngine, providing accumulated aggregates (summed or otherwise combined output values), provenance (which original rules contributed to each combination, identified by prime products), and depths (how many rules are in each combination). AccumulatorResult does not have specificity scoring or ranking in the same sense as RuleResult because its combinations are not competing alternatives but rather different accumulation scenarios. The provenance accessor is the AccumulatorEngine's equivalent of explain: it tells you exactly which rules were combined to produce each accumulated value by factoring the prime product back into its constituent primes.

### What is the Aggregate model and how is it used?

The Aggregate model is a Pydantic model that defines how output values should be accumulated when rules are combined in the AccumulatorEngine. It specifies a source column (the rule table column containing the values to accumulate), an aggregation function (such as sum, which adds values across combined rules), and an output column name. When the lattice is built, accumulated aggregate columns are computed for each combination by applying the aggregation function to the source column values of the constituent rules. For example, an Aggregate with source="discount_pct" and function=sum would produce a column containing the total discount percentage for each rule combination. Multiple aggregates can be defined, allowing the engine to accumulate several output values simultaneously. The Aggregate model validates that source columns exist and aggregation functions are supported.

## Practical Usage and Best Practices

### How do I define a simple rule evaluation with ExpressionRulesEngine?

Start by defining your dimensions. Create Dimension objects for each matching criterion, specifying the match strategy and column names. Assemble them into a DimensionsMetadata collection. Prepare your rule table as a DataFrame with columns matching the dimension field references plus your output columns. Create an ExpressionRulesEngine with the DimensionsMetadata. Call the engine's evaluate method with your context dictionary mapping dimension names to values. The returned RuleResult gives you access to survivors, the best match, and explanations. A minimal example might have two EXACT dimensions (region and product), one RANGE dimension (amount with low and high columns), and an output column (price). The context provides {"region": "US", "product": "widget", "amount": 150}, and the engine returns the most specific matching price rule.

### How do I set up the AccumulatorEngine for a benefits accumulation problem?

For a benefits accumulation problem, first identify your CONSTRAINT dimensions (the criteria that determine rule compatibility, such as benefit_category, region, and tier) and your CONTEXT_KEY dimensions (such as customer_id, which partitions rules by customer). Define Dimension objects for each and assemble them into DimensionsMetadata. Define Aggregate objects for the values to accumulate (such as benefit_value with sum aggregation). Create an AccumulatorEngine with the DimensionsMetadata and Aggregates. Call build_all to build lattices for all partitions. When a context arrives, call apply_auto with the context (including the customer_id), which selects the correct partition lattice and returns an AccumulatorResult containing all maximal consistent benefit combinations with their accumulated values and provenance.

### How should I choose between EXACT, RANGE, and other match strategies for a dimension?

Choose the strategy based on the nature of the dimension's data and the matching semantics you need. Use EXACT for categorical values with discrete membership (country codes, product SKUs, status flags). Use RANGE for continuous numeric intervals (age bands, price tiers, date ranges) where the rule defines a low-high window. Use GREATER_THAN or LESS_THAN for one-sided thresholds (minimum order value, maximum age). Use PREFIX for hierarchical codes where broader categories should match their children (matching "US" against "US-CA", "US-NY"). Use SET_MEMBERSHIP when a single rule should match multiple discrete values without duplicating rows. Use REGEX for complex pattern matching when simpler string strategies are insufficient. Use CONTAINS for substring matching. Use NOT_EQUAL for exclusion-based matching (all regions except "EU"). Use SET_EXCLUSION for excluding multiple values. The choice affects sentinel handling, specificity scoring, and compilation behavior, so select the strategy that most naturally represents the business semantics.

### How do I make rules explainable for audit or compliance purposes?

Mountainash-rules has explainability built into both engines. For the ExpressionRulesEngine, call RuleResult.explain() to get per-dimension ternary outcomes for any rule, showing exactly which dimensions matched (TRUE), contradicted (FALSE), or were indeterminate (UNKNOWN). Log the full evaluated DataFrame with observability columns (__survived, __specificity, __rank) for audit trails. For the AccumulatorEngine, use AccumulatorResult.provenance to identify exactly which original rules were combined in each accumulation, with prime product factorization providing an unambiguous record. Combine provenance with the Lattice's coalesced columns to see the merged dimension values for each combination. For compliance scenarios, you can store the full RuleResult or AccumulatorResult alongside the business decision, providing a complete trace from input context through matching logic to output decision. The ternary logic model makes explanations precise: unlike binary match/no-match systems, you can distinguish between "this rule definitely matched" and "this rule might have matched but we lacked information."

### What are common pitfalls when designing rule tables?

Several pitfalls are common. First, forgetting sentinel values: if a "wildcard" rule has an empty string instead of null in a numeric column, the sentinel detection may not recognize it, causing unexpected FALSE outcomes. Ensure sentinel values match the expected type (null for all types, empty string for strings, numeric sentinels for numbers). Second, overlapping RANGE intervals without clear specificity: if two rules have overlapping ranges and equal specificity on other dimensions, they tie in ranking, which may produce ambiguous results. Third, excessive rule table size for the AccumulatorEngine: the combinatorial expansion is exponential, so hundreds of rules in a single partition can cause performance issues or prime product overflow. Use CONTEXT_KEY partitioning to keep partitions small. Fourth, mismatched data types between the context and rule columns, which can cause unexpected comparison failures. Fifth, defining REGEX patterns that are valid in one backend but not another, which undermines backend portability. Validate rule tables against the DimensionsMetadata schema before evaluation.

### How do I handle rules that should not combine in the AccumulatorEngine?

If certain rules should never be combined (for example, two mutually exclusive discount types), model this through dimension constraints rather than special engine configuration. Add a dimension that distinguishes the exclusive groups, such as a "discount_type" dimension with EXACT strategy. Rules with different discount_type values will be incompatible on that dimension and will never appear in the same combination. Alternatively, if the exclusion is based on a business key (like customer segment), make that dimension a CONTEXT_KEY, which partitions rules so they are never combined across partitions. The AccumulatorEngine relies entirely on dimension compatibility to determine valid combinations, so the way to prevent unwanted combinations is to ensure the dimension model makes them incompatible. This is a deliberate design choice: the compatibility logic is explicit in the data model rather than hidden in engine configuration.

### How do I evaluate many contexts against the same rule table efficiently?

For the ExpressionRulesEngine, use the advanced construction path. Create the engine once with DimensionsMetadata, which pre-compiles all dimension expressions. Then call evaluate repeatedly with different contexts. The compiled expressions are reused, avoiding redundant compilation. For the AccumulatorEngine, build the lattice once using build_all (which builds lattices for all partitions), then call apply_auto repeatedly with different contexts. The lattice is the expensive part; applying a context to it is comparatively cheap. Store the built Lattice objects and reuse them across evaluations. If the rule table changes, you must rebuild the engine or lattice, but if only contexts change, reuse is safe. This separation of build and apply is a key architectural pattern in mountainash-rules.

### Can I use both engines together in a single evaluation pipeline?

Yes, and this is a common pattern for complex business logic. Use the ExpressionRulesEngine for selection problems (find the applicable pricing tier, determine the customer's eligibility category) and the AccumulatorEngine for accumulation problems (calculate total benefits, stack applicable discounts). The output of one engine can feed into the context of the other. For example, the ExpressionRulesEngine might determine that a customer is in the "premium" tier, and this tier value is then included in the context for the AccumulatorEngine to accumulate the applicable premium benefits. Both engines share the same DimensionsMetadata model and mountainash expression system, so dimension definitions are consistent across both. This composability is intentional: real business logic rarely falls neatly into a single evaluation pattern.

### What should I know about performance and scalability?

The ExpressionRulesEngine scales linearly with the number of rules because it performs a single vectorized pass over the rule table. Thousands of rules evaluate in milliseconds. The number of dimensions affects compilation time (one expression per dimension) but has minimal impact on evaluation time. The AccumulatorEngine's lattice building phase is combinatorial and can be expensive. The number of valid combinations grows exponentially with the number of compatible rules in a partition. Partition sizing is the primary performance lever: use CONTEXT_KEY dimensions to keep partitions under approximately 20-30 rules to avoid prime product overflow and excessive lattice sizes. Lattice application (applying a context to a pre-built lattice) is fast, comparable to ExpressionRulesEngine evaluation. For both engines, backend choice affects raw speed: Polars is typically faster for in-memory evaluation, while Ibis backends enable evaluation against database-resident rule tables without materializing them into memory.

### How does mountainash-rules handle null values in rule table columns?

Null values in rule table columns are treated as sentinels, meaning "no constraint" or "don't care" for that dimension. The DimensionCompiler generates sentinel-aware ternary expressions that check for nulls before performing comparisons. When a null is detected in a rule column, the expression evaluates to UNKNOWN (0) rather than attempting a comparison that would fail or produce incorrect results. This is consistent across all match strategies: a null in an EXACT column means "match any value," a null in a RANGE low_field means "no lower bound," and a null in a SET_MEMBERSHIP column means "match any value." The distinction between null and empty string matters: for string dimensions, both null and empty string are sentinels, but for numeric dimensions, only null and the special numeric sentinel values are recognized. Ensure your rule table uses the correct sentinel representation for each column's data type.

### How do I validate that my DimensionsMetadata and rule table are consistent?

DimensionsMetadata performs validation at definition time through Pydantic validators and the Dimension Validator. This catches strategy-datatype mismatches, missing field references, duplicate dimension names, and invalid CONTEXT_KEY configurations. However, metadata validation does not check against the actual rule table schema. To validate consistency between metadata and data, verify that all field names referenced in dimensions exist as columns in the rule table, that column data types match the expected types for each strategy, and that sentinel values are correctly represented. You can do this programmatically by comparing the metadata's expected columns against the DataFrame's column names and types. Running a test evaluation with a known context and expected outcome is also a practical validation step. If the evaluation produces unexpected results, the explain method will show which dimensions are producing incorrect ternary outcomes, helping you identify mismatches.
